# Working in packages/orchestrator/

- Source in `src/` with one subdirectory per feature: `inbox/`, `json-schema-to-zod/`, `main-turn/`, `mcp/`, `models/`, `plan/`, `prompts/`, `registries/`, `runtime/`, `types/`, `tools/`. Each folder has `index.ts` (barrel), implementation files, `README.md` (Chinese) and `AGENTS.md` (English); tests in `test/*.test.ts`. `src/index.ts` is the package entry (re-exports only) and deliberately keeps `tools/run-worker.ts` and `tools/spawn-tasks.ts` internal.
- May depend on `@hotpot/core` (`workspace:*`) and `@hotpot/ai` (`workspace:*`); never import from `@hotpot/cli`.
- This package holds the three-layer agent orchestration: the main agent (conversation entry, first-turn prompt routing by difficulty/model tier), worker agents (execution and parallel split), and task agents (atomic subtasks); plus the plan approval flow and the steer/queue dual-queue mechanism.
- Dependency direction is fixed: `orchestrator → core → ai`. Never add a reverse edge.
- LLM-facing prompt text is English; code comments in Simplified Chinese.
- M4: `createRoleRegistry(runtime, role, metaTools)` derives worker/task tools from `runtime.features` (todo / web / MCP) while main stays meta-tools-plus-read (M1: `read` is main's only file tool, registered plain — no decoration, no skill tracking). Todo prompt sections come from `foldTodos` at prompt-build time; skill sections come from `runtime.skills` and are tracked by a read-tool wrapper that appends `skill/loaded`; `runtime.hooks` must be threaded into every `LoopConfig`, with `turn_end` fired once per turn by `runMainTurn` / `runAgentInline`.
- M1 permission modes: `permission.mode` (`readonly` / `ask-on-dangerous` / `full`, default `ask-on-dangerous`) lives in a mutable `runtime.permissionMode` holder; assembly layers pass the same holder to `createPermissionModeDecorator`, which dispatches at execute time (readonly pre-approves non-read worker tools; ask-on-dangerous/full pass through, with `full` prepending core's `allowAllHandler` to the approval chain).
- Plan flow: the initial turn's plan output (validated by `detectPlanDraft` — `# Plan` heading plus the Steps/Files/Acceptance criteria sections, newest marked message in the turn window) routes the turn into `runPlanPhase`, which reuses it and only drafts when the plan is missing or the `next-step` queue is non-empty. The plan phase registers no tools; the execution phase registers only `spawn_workers`. Internal plan prompts are persisted as `internal_msg` (folded into model history, not rendered by UI), and `plan(drafted)` events carry `messageIds` so the web can hide the duplicate plan text.
- Erasable TypeScript only, `.ts` extension on relative imports, no `any`, no inline imports.
- Verify with `pnpm test` and `pnpm exec biome check` from the repo root before committing.
